# DeskBeam

Share a Windows desktop at up to 60 fps and let a remote player join with an Xbox controller.
While a viewer is connected, the host creates a **virtual Xbox 360 pad** with ViGEmBus, so games
running on the host see the remote controller exactly like a locally plugged-in gamepad.

- Avalonia desktop apps for host and viewer
- Windows Graphics Capture (WGC) by default, with DXGI Desktop Duplication and GDI fallbacks.
  WGC is composed by DWM, so it keeps working across game resolution, refresh-rate and HDR
  switches, and it does not silently stop like duplication can when a game takes the display.
  Select the API in the host if you need to troubleshoot.
- HDR-aware capture: scRGB (FP16) and HDR10 (PQ/BT.2020) surfaces are tone-mapped on the GPU to
  correct SDR before encoding, so the viewer never gets the pink/green garbage or washed-out
  colours that come from reading HDR surfaces as 8-bit BGRA
- SkiaSharp JPEG keyframes with 64×64 dirty-tile deltas: a mostly static desktop sends only the
  patches that changed instead of a full frame, while full-screen motion falls back to keyframes
- Adaptive quality: when the viewer cannot receive 60 fps, it asks the host for a lower
  resolution/quality (and finally 30 fps) instead of building a multi-second latency backlog
- Separate control + video TCP channels, length-prefixed framing
- Low-latency desktop audio on its own UDP channel (Opus, 10 ms frames) with Discord excluded
- HMAC-SHA256 PIN challenge (the PIN itself never crosses the wire)
- UPnP port mapping built in (no router software, no extra dependency)
- Raw XInput polling on the viewer at 100 Hz, rumble forwarded back
- Remote mouse + keyboard injection (optional)

## Requirements

| Item | Notes |
| --- | --- |
| Windows 10/11 | DXGI Desktop Duplication is Windows-only |
| .NET 10 SDK | `dotnet --version` should report 10.x |
| [ViGEmBus](https://github.com/nefarius/ViGEmBus/releases) | Needed on the **host** for the virtual Xbox pad. Install once, reboot. |
| Xbox controller | Plugged into the **viewer** PC (XInput) |
| Opening ports | Control `47777` and video `47778` (TCP), audio `47779` (UDP) by default |

No ViGEmBus is needed if you only want video and mouse/keyboard.

## Build

```powershell
cd L:\Work\DeskBeam
dotnet build DeskBeam.slnx
```

GitHub Actions also builds the solution and uploads self-contained Windows x64 Host and Client
ZIPs on pushes and pull requests. To publish a release, run **Build and release** from the
Actions tab, select the branch to release, and enter a new tag such as `v1.2.3`. Optionally mark
it as a prerelease. The workflow tags the selected commit and publishes both ZIPs with generated
release notes. Tags must be new; if release creation fails after the tag is created, remove or
otherwise handle that tag before retrying. Extract each ZIP before running its executable; the
.NET runtime is included, but the host still needs ViGEmBus for controller support.

End-to-end headless check (starts a host, rejects a wrong PIN, streams keyframes and delta tiles,
checks composition and JPEG decode, ping, stats, shutdown):

```powershell
dotnet run --project tools\DeskBeam.Smoke -c Release
```

Add `-- --upnp` to also exercise router port mapping, `-- --input` to verify pointer injection
(moves the real cursor to the monitor centre and back), or `-- --dump` to save the last decoded
viewer frame as `deskbeam-smoke-frame.png` in the temporary directory. The dump is useful for
checking colour conversion on HDR displays. Use `-- --capture=wgc` (or `dxgi` / `gdi`) to force a
capture path, `-- --monitor=1` to capture a different display, and `-- --soak=20` to keep streaming
for 20 seconds (for example while changing the display mode in Windows settings).
`-- --controller-only` starts the host with mouse/keyboard forwarding off and checks that the
virtual Xbox pad is still created, which is the layout most game-streaming hosts want.
`-- --audio` enables the audio channel, binds the viewer's UDP socket, verifies that the host
recognises the endpoint and reports how many Opus packets arrived. The Opus round-trip itself is
always tested, even without an audio device.

## Run the host

```powershell
dotnet run --project src\DeskBeam.Host
```

1. Pick the monitor, capture API, capture size and frame rate (1280×720 @ 60 fps by default).
   **Auto** starts with Windows Graphics Capture and falls back to DXGI Desktop Duplication and
   then GDI if an API is unavailable. Pick **DXGI** manually if you want the lowest overhead on a
   static desktop; pick **Windows Graphics Capture** when a game causes DXGI to stop producing
   frames.
2. Keep the generated PIN or press **New PIN**.
3. Press **Start host**.
4. Share the address shown under **Share this address** and the PIN.

The pipeline card shows capture fps, encode time, bitrate and output resolution. The player list
shows who is connected and whether their video, audio and pad channels are live. Capture
diagnostics are also written to `%APPDATA%\DeskBeam\host.log` (rotated at 4 MB), so you can
reproduce a problem, close the host and still inspect what happened.

### Desktop audio

Audio is on by default; clear **Stream desktop audio** in the host if you want video only. Pick a
bitrate (64 kbps is a good default; 96–128 kbps suits music) and keep the excluded-app list at
`Discord, DiscordPTB, DiscordCanary, DiscordDevelopment`. Capture starts when the first viewer
connects and stops when the last one leaves, so an idle host never holds the audio device.

The exclusion list uses WASAPI process loopback, which removes that application's whole process
tree (including Discord's helper processes) from the captured mix **without muting Discord
locally**. If none of the listed apps is running, DeskBeam excludes its own process tree as a
neutral target; it never falls back to full system loopback, so an accident cannot leak Discord
audio.

Audio always yields to video:

- Audio uses UDP on `control + 2`; video stays on TCP, so a lost audio packet can never delay or
  reshape a video frame.
- The encoder runs on a below-normal-priority thread with a short (80 ms) queue that drops old
  frames instead of growing latency.
- The viewer reports loss and jitter once per second. If a viewer is congested, the host mutes
  **audio for that viewer** for five seconds while the video stream keeps its current settings.
- Viewer latency is bounded: about 40 ms of WASAPI buffer plus at most six queued 10 ms frames.
  Playback keeps a two-frame jitter window so a slightly early frame is waited for rather than
  concealed, a frame older than that window is concealed immediately, and the oldest frames are
  shed if a burst would push the queue past that bound. Concealment uses Opus in-band FEC from the
  next packet when it is available.

Enable/disable and the port need a host restart; bitrate and the exclusion list apply live.

Settings are stored in `%APPDATA%\DeskBeam\host.json`.

## Run the viewer

```powershell
dotnet run --project src\DeskBeam.Client
```

1. Enter host address, control port and PIN.
2. Press **Connect** (or **Disconnect** to close the session).
3. Click the video once so it owns the keyboard.

Useful toggles while connected: **Forward mouse**, **Forward keyboard**, **Mute audio**, **Stats**.

The stats line shows received fps, bitrate, decode time and RTT, plus audio packets/second, loss,
jitter and playback buffer when the host offers audio. When the link cannot sustain the
current quality, the viewer automatically steps down its requested resolution/quality and reports
`adaptive 1024x576 q45` (or similar) next to the metrics. On a fast link it steps back up after a
short probe delay, so a transient stall does not permanently weaken the picture.

Settings are stored in `%APPDATA%\DeskBeam\client.json`.

### Controller

Plug an Xbox controller into the viewer PC before connecting.
On the host, **Gamepad status** changes to `Virtual Xbox 360 pad active.` and the pad appears in
`joy.cpl` / the Windows Game Controllers list for as long as the viewer is connected.
Button mapping follows XInput exactly (triggers are analog, rumble is sent back to the viewer).

## Internet play

**Automatic (recommended):** enable UPnP on the router, then press **Map ports with UPnP** in the
host. When it succeeds the share address becomes `public-ip:control-port`, and the mappings are
removed again when the host stops.

The mapper searches every local IPv4 interface (so it works with Hyper-V, VPN and multi-NIC
machines), retries the SSDP search, honours `<URLBase>` in device descriptions, removes stale
mappings for the same port before adding, and then verifies that the gateway accepted the control
and video mappings. Audio gets a UDP mapping as a best effort: if the router refuses it the video
session still works, but audio is LAN-only and the result message says so. If mapping still
fails, see **UPnP mapping failed** below.

**Manual:** forward both TCP ports and the UDP audio port to the host PC:

| Port | Protocol | Purpose |
| --- | --- | --- |
| `47777` (control) | TCP | handshake, input, stats, ping, audio reports |
| `47778` (control + 1) | TCP | JPEG video stream |
| `47779` (control + 2) | UDP | Opus desktop audio (one-way, host → viewer) |

If you change the control port, video is always control + 1 and audio control + 2.

**Firewall:** allow inbound TCP on both TCP ports and inbound UDP on the audio port for the
private network (and public if the router maps traffic). Running the host as administrator once
lets Windows show the firewall prompt for the app. Alternatively:

```powershell
netsh advfirewall firewall add rule name="DeskBeam control" dir=in action=allow protocol=TCP localport=47777
netsh advfirewall firewall add rule name="DeskBeam video"   dir=in action=allow protocol=TCP localport=47778
netsh advfirewall firewall add rule name="DeskBeam audio"   dir=in action=allow protocol=UDP localport=47779
```

### Security and privacy

- Authentication uses an HMAC-SHA256 challenge/response over a random nonce; the PIN is never
  transmitted and each connection needs a fresh proof.
- The JPEG stream, desktop audio, mouse/keyboard input and controller state are **not encrypted**
  in this version. Use DeskBeam on a trusted LAN, or tunnel it through a VPN such as WireGuard,
  Tailscale or ZeroTier when playing over the internet.
- Treat the PIN like a session password. Press **New PIN** between players.

## Bandwidth and HDR

Video is JPEG over TCP, but only a viewer's first frame (and the occasional refresh) is a full
image. Normal frames are 64×64 JPEG tiles covering just the regions that changed since the previous
frame. Traffic therefore tracks how much of the desktop moves, not only the quality setting. Rough
1280×720 @ 60 fps numbers on a typical desktop:

| Content | Typical traffic |
| --- | --- |
| Static desktop, cursor, clock, typing | ~0.2–3 Mbps |
| Scrolling, dragging windows, a small video | ~3–10 Mbps |
| Full-screen video or fast game | full-frame cost below (~40–60 Mbps) |

When more than half of the canvas changes, the host sends one full keyframe instead of many small
tiles, so full-screen motion degrades gracefully to the intra-JPEG cost rather than paying per-tile
overhead. In that case quality sets the bitrate:

| Quality | Full-frame bitrate | Comfortable upload |
| --- | --- | --- |
| 45 | ~40–55 Mbps | 65 Mbps |
| 55 (default) | ~46–63 Mbps | 75 Mbps |
| 75 | ~60–85 Mbps | 100 Mbps |

The viewer starts remote (non-LAN) sessions at a conservative size and bitrate, then measures the
delivered frame rate, skipped-frame ratio and RTT. If the link is short it asks the host for a
smaller stream: the ladder runs from the host default down through 0.9×, 0.8× … 0.3× resolution
with quality 55 → 28, and finally 30 fps. This keeps the picture live at 60 fps (about
640×360 q38 on a 12 Mbps upstream) instead of showing 1–10 fps with growing delay. If you have
more upstream, use the host's **Quality** and **Capture size** settings as the starting point; the
viewer only scales down from there.

A viewer that joins an idle desktop gets the host's last encoded frame immediately (re-emitted as a
keyframe from memory), then deltas as soon as anything changes. A skipped delta is repaired with a
fresh keyframe rather than showing a corrupt composite.

Audio adds ~64 kbps. On a static desktop that is a noticeable share of very low video traffic, but
it is still cheap next to full-motion video and is carried on UDP, dropped independently, and never
allowed to block the video channel.

A few practical notes:

- Leave ~30% upstream headroom for full-screen motion. A 20 Mbps upload cannot carry a 40 Mbps
  game stream reliably once other traffic shares the link.
- The host drops stale frames instead of queuing them, and the video socket's send buffer is
  bounded, so a slow link settles quickly instead of accumulating seconds of latency.
- On a LAN the viewer keeps the host's full quality; adaptation only kicks in when frames are
  actually being lost.
- HDR monitors are handled automatically: the host logs `HDR scRGB (FP16)` or `HDR10 PQ` and
  tone-maps to SDR using the display's real SDR white level (read from DisplayConfig). SDR output
  is passed through untouched. No manual setting is needed, and switching HDR on/off while
  streaming is handled per frame.

### Why TCP, JPEG, and tile deltas (for now)

The video channel is TCP because delta tiles only make sense in order: losing one would corrupt
every later frame until a keyframe. TCP already guarantees that order, and the host's policy of
sending only the newest frame keeps latency bounded under backpressure. A keyframe is a complete
JPEG, so recovering from a gap costs exactly one frame; the host detects a viewer that fell behind
and substitutes its cached keyframe, and the viewer can also send `KeyframeRequest` explicitly.

A real interframe codec (H.264/HEVC) is the next step for full-screen motion: it can describe motion
between frames far better than independent JPEG tiles. The encoder is behind `IVideoEncoder`, and
`JpegTileEncoder` is the current implementation, so an MFT/AMF-backed encoder can be added without
changing the viewer's transport, keyframe recovery, or UDP audio design. Until then the tile codec
keeps the all-managed build and makes the common desktop case cheap.

Audio is the opposite case: 10 ms Opus frames are small, independently decodable and loss-tolerant,
so UDP plus a tiny jitter buffer gives lower latency and cannot head-of-line block the video
socket. That separation is the whole point of the third port.

## Architecture

```
src/DeskBeam.Core      protocol, framing, auth, JPEG keyframe/tile codec, Opus audio wire format,
                       UPnP, settings
src/DeskBeam.Engine    WGC/DXGI/GDI capture, encoding pipeline, desktop audio capture,
                       input injection, ViGEm virtual pad, host server and sessions
src/DeskBeam.Host      Avalonia host UI
src/DeskBeam.Client    Avalonia viewer UI (XInput, WriteableBitmap presenter)
tools/DeskBeam.Smoke   headless end-to-end test
```

Flow:

1. Viewer connects to the control port; host sends `ServerHello` with a nonce.
2. Viewer answers with `AuthRequest` (HMAC proof + name); host validates the PIN.
3. Host replies `AuthResult` + `StreamInfo` (video port, session token, size, fps, quality).
4. Viewer opens the video port, presents the session token, and receives a keyframe followed by
   changed-tile deltas. It sends `KeyframeRequest` if it misses a frame.
5. If audio is enabled, the viewer sends its session token to the UDP audio port to bind an
   endpoint; the host answers with 20-byte-header Opus packets and the viewer reports
   loss/jitter/mute once per second on the control socket.
6. Viewer sends `GamepadState`, `PointerInput`, `KeyInput` and `Ping` on the control socket.
7. Host injects input, updates the ViGEm pad, and broadcasts `HostStats` + `RumbleState`.

## Troubleshooting

**"Virtual Xbox controller unavailable"** — ViGEmBus is missing or not loaded. Install it from
the link above and reboot. Video and mouse/keyboard still work without it.

**No video / black window** — check that both TCP ports are reachable (`Test-NetConnection host
-Port 47777`). On the host, verify the log says which capture path is in use. Windows Graphics
Capture is the default; if a driver or a restricted session blocks it, the host falls back to DXGI
Desktop Duplication and then GDI. You can force a path under **Capture API** in the host.

**A game drops the stream to 0 fps** — work through these in order:

1. Check `%APPDATA%\DeskBeam\host.log`. A mode switch logs `Display size changed ... recreating
   capture`, followed by a fresh `Windows Graphics Capture ready`. That is recovery, not a
   failure.
2. Make sure the game is on the monitor selected in the host. DeskBeam captures one display; if
   the game opens on the other monitor, the captured desktop is static and the viewer sees no
   motion.
3. Set the game to **borderless / windowed fullscreen** (sometimes called "Fullscreen Window" or
   "Borderless"). Exclusive fullscreen presents directly to the display and bypasses DWM, so
   neither Windows Graphics Capture nor Desktop Duplication can see it on Windows 11 24H2+. This is
   the same limitation OBS and other desktop-capture tools have.
4. Try switching **Capture API** between **Windows Graphics Capture** and **DXGI Desktop
   Duplication** while the game is running. WGC survives mode/refresh/HDR changes more reliably.
5. A static desktop legitimately produces no new frames: WGC and Desktop Duplication are
   change-driven. Do not treat `0 fps` on an unchanging screen as a failure. If the screen is
   changing and the viewer still shows nothing, check the log for `Capture error` or a closed
   capture item, update the GPU driver, and retry in borderless mode.

**Pink/green blocks or wrong colours** — this was caused by reading HDR surfaces as 8-bit BGRA.
Current builds tone-map HDR on the GPU; the host log should say `HDR scRGB (FP16)` or `HDR10 PQ`
when the desktop is in HDR. A truncated keyframe or tile is rejected and the viewer requests a
fresh keyframe instead of displaying a partial image. If you still see colour problems, run the
smoke test with `--dump` and inspect the saved PNG.

**Low frame rate over the internet (1–10 fps)** — the upstream is saturated. The viewer adapts
automatically within a few seconds; the stats line shows the reduced `adaptive` size and quality.
If it does not recover, lower **Quality** or **Capture size** on the host, or confirm the actual
upload speed. A large backlog can also come from another app saturating the same link.

**No audio on the viewer** — enable **Stream desktop audio** in the host and restart the host
(enable/disable is a start-up setting). Check the host log for `Capturing desktop audio` and make
sure UDP `control + 2` is allowed through Windows Firewall and, for internet play, forwarded on
the router. The viewer's stats line shows audio packets/second; zero packets while the host reports
`Capturing desktop audio` means the UDP path is blocked. Remember that the host is capturing a
playback endpoint: if Windows is muted, the loopback is silent too.

**Audio stutters while video stays smooth** — this is intentional isolation. Audio is allowed to
drop; video is not. Lower the audio bitrate, reduce jitter on the link, or use a wired LAN. The
host mutes audio for a viewer that reports more than 25% loss or 150 ms jitter for two consecutive
seconds, then retries after five seconds without changing video settings.

**Discord can still be heard** — check that the process list in the host matches Task Manager
exactly (`Discord`, `DiscordPTB`, `DiscordCanary`, `DiscordDevelopment`; `.exe` is optional and
copy/paste is fine). Capture excludes the matching process tree, not just the main window, but a
separate voice client or browser tab playing Discord in another app is not covered. Add that
application's executable name to the list. If Discord is not running, DeskBeam excludes its own
process tree rather than falling back to full system audio.

**Controller not detected on the viewer** — XInput must see it before connecting. Test it in
`joy.cpl`. The viewer polls controller slots 1–4.

**UPnP mapping failed** — many routers require UPnP/IGD to be enabled explicitly (look for
"UPnP", "NAT-PMP" or "Internet Gateway Device" in the router UI). Some guest Wi-Fi networks and
mesh nodes block SSDP entirely. Forward the two TCP ports (and UDP audio) manually instead; the
host log shows the internal LAN IP to forward to. If the router reports an existing mapping,
DeskBeam removes and re-adds it automatically.

**Firewall prompt every start** — run the host once as administrator and allow access for both
private and public networks.

## Notes

- The protocol version is in `src/DeskBeam.Core/Protocol/ProtocolConstants.cs`; bump it when
  message shapes change. Version 2 added the audio fields to `StreamInfo`, `AudioReport` and the
  audio stats on `HostStats`. Version 3 replaced whole-frame JPEG video with keyframes plus
  changed-tile deltas and added `KeyframeRequest`.
- The host supports multiple viewers; the virtual pad is created per session, so several
  controllers can be active at once.
- Adaptive streaming uses the existing `RequestStream` control message, so no protocol bump is
  needed. It applies to the host's single capture pipeline; when the last viewer disconnects the
  host restores its configured size, fps and quality for the next session.
- `DeskBeam.Smoke` covers the protocol, capture pipeline, tile encode/composite and wire round
  trip, Opus encode/decode, the virtual pad, ping and clean shutdown, and can run on a build
  server without a viewer UI (pass `--input` to also check real cursor injection, `--dump` to save
  a decoded frame, `--audio` to bind the UDP channel, `--capture=` to force a capture API and
  `--soak=` to keep the stream open while you change display modes).
- The pipeline fingerprints a sparse pixel grid only for GDI, which repeats a frame at the
  requested fps even when nothing changed. WGC and Desktop Duplication are change-driven, so their
  frames are encoded as they arrive; skipping them with a sparse hash could lose a small update
  such as a moving cursor. Delta encoding means an unchanged region costs nothing even when a
  change-driven backend does emit a frame.
